# 前端开发文档：发财·美容店智能客户账本

版本：v1.0  
状态：开发基线·已确认  
日期：2026-08-20

## 1. 文档目的

本文档将已经确认的产品需求、视觉方向和交互原型转换为可执行的前端开发规范，覆盖：

- 页面与信息架构；
- 聊天内解析确认流程；
- 客户、服务类型和服务详情的分层查看；
- 视觉设计系统；
- 组件、状态和响应式规则；
- 前后端接口边界；
- 分阶段开发、验证链接和验收标准。

本文档不代表已经开始开发。正式开发仍需用户明确回复“确认开始开发”。

## 3. 产品与设计目标

### 3.1 使用目标

让单人经营美容店的店主在手机场景下：

1. 像聊天一样输入购买、核销或查询；
2. 在聊天消息中查看Agent解析结果；
3. 修改核销次数和日期；
4. 确认后写入账本并看到新余额；
5. 从客户账本逐层查到某位客户的某项服务详情。

### 3.2 体验原则

- 输入为核心，首页不堆叠经营数据；
- 写入前必须清楚确认；
- 重要数据同时显示“本次变化”和“变化后结果”；
- 客户服务较多时逐层展开，不在一个页面堆完；
- 界面简单、克制、可快速扫描；
- 颜色只用于主操作、状态和关键信息；
- 不使用大面积渐变、玻璃拟态、3D按钮或装饰性插画。

## 4. 目标设备与页面容器

### 4.1 移动端优先

- 主要设计宽度：390px；
- 必须支持：360px～430px；
- 使用手机浏览器或微信内WebView时占满可用宽度和高度；
- 考虑底部安全区 `env(safe-area-inset-bottom)`；
- 输入区域不得被软键盘永久遮挡。

### 4.2 本地电脑测试

- 桌面浏览器中将移动端应用区域居中展示；
- 推荐最大内容宽度430px；
- 不在正式产品代码中绘制假手机黑框或刘海；
- 验证说明可以放在应用区域旁边，但生产页面不显示说明栏。

## 5. 信息架构

```text
对话首页
├── 自然语言输入
├── 对话消息
├── 解析确认卡
└── 写入结果

客户账本 Sheet
├── 客户搜索
├── 客户列表
└── 客户概览
    ├── 客户基本信息
    ├── 服务类型列表
    └── 最近动态
        └── 服务详情
            ├── 套餐卡列表
            ├── 使用与余额
            └── 该服务历史

其他入口
├── 服务项目管理
├── 回收站
└── 系统提示词管理
```

说明：

- 客户列表不直接展开全部套餐；
- 客户概览按“服务类型”聚合；
- 同一服务存在多张套餐卡时，在服务详情中分别展示；
- 一次性服务也作为服务类型显示，但不展示套餐余额。

## 6. 导航结构

底部导航包含：

1. **对话**：默认首页；
2. **客户**：打开客户账本 Sheet；
3. **设置**：进入服务管理、回收站和系统提示词管理。

测试版不增加更多一级导航。

## 7. 对话首页

### 7.1 顶部区域

展示：

- “发财”标识和名称；
- 副标题“智能客户账本”；
- 搜索入口；
- 快速新增入口。

顶部保持固定，聊天区域独立滚动。

### 7.2 消息类型

必须支持以下前端消息类型：

- 店主文本消息；
- Agent普通回复；
- 待澄清问题；
- 客户候选列表；
- 新客户创建确认；
- 结构化操作确认卡；
- 写入成功结果；
- 写入失败或规则冲突；
- 模型或网络错误。

### 7.3 输入区

- 固定在底部导航上方；
- 支持文本输入；
- 店主可使用手机输入法语音转文字；
- 空内容不能提交；
- 请求期间显示解析状态，防止重复提交；
- 输入发送后保留原始文本消息；
- 显示提示：“AI可能理解有误，写入前会请你确认。”

## 8. 聊天内解析确认

### 8.1 展示位置

解析结果作为Agent消息显示在聊天流中，不使用独立的全屏确认页，也不使用与聊天脱离的底部弹层。

### 8.2 单项套餐核销确认卡

必须展示：

- 客户名称；
- 服务名称；
- 操作类型；
- 本次核销次数；
- 核销日期；
- 确认后的累计使用次数；
- 总次数；
- 确认后的剩余次数；
- “修改”和“确认入账”按钮。

示例：

```text
小蓝 · 肩颈按摩
识别为套餐核销1次

本次核销：1次
核销日期：2026年8月20日
确认后：累计使用2/3次，剩余1次

[修改] [确认入账]
```

### 8.3 修改状态

点击“修改”后，卡片内展开可编辑区域：

- 核销次数：正整数；
- 核销日期：日期选择器；
- 必要时选择客户、服务或具体套餐卡。

修改后必须重新请求后端预检查，不能只在前端自行计算并直接提交。

### 8.4 确认写入

点击“确认入账”时：

1. 按钮进入加载状态；
2. 防止重复点击；
3. 后端重新校验客户、套餐和余额；
4. 成功后卡片转换为只读成功状态；
5. 显示实际入账日期、实际余额和查看路径；
6. 同步刷新客户列表、客户概览和服务详情缓存。

成功示例：

```text
已于2026年8月20日入账
肩颈按摩累计使用2/3次，剩余1次。
可在“客户 → 小蓝 → 肩颈按摩”中查看。
```

### 8.5 多项操作

一句话包含多项服务或商品时：

- 在同一条Agent回复中按明细拆分；
- 每项显示独立的操作类型、数量和结果；
- 店主可以逐项修改或移除；
- 最终提供统一确认入口；
- 某一项存在歧义时，不影响店主查看其他项目，但必须先解决该项或将其移除，才能最终确认；
- 最终确认后的剩余项目作为一个整体提交：全部成功入账，或任一项失败时全部不入账；
- 失败时保留卡片和修改内容，展示具体失败项目，不让店主重新输入整句话。

### 8.6 一次性服务

确认卡显示：

- 客户；
- 服务；
- 次数；
- 消费日期；
- 可选价格；
- 提示“本次为一次性服务，不计算套餐余额”。

### 8.7 商品购买

确认卡显示：

- 客户；
- 商品名称；
- 数量；
- 可选价格；
- 购买日期。

不显示库存信息。

## 9. 客户匹配交互

### 9.1 唯一近似客户

同时展示：

- 客户化名和别名；
- 与本次问题有关的服务信息；
- “请问是这位客户吗？”；
- 确认或重新选择按钮。

### 9.2 多个近似客户

- 最多展示匹配度最高的3位；
- 每位展示化名、别名和本次查询相关信息；
- 提示：“有多个近似客户，本次为您展示前3位，请问有您咨询的客户吗？”；
- 店主选择后继续原流程。

### 9.3 新客户

不存在客户时，在聊天中展示解析到的：

- 新客户名称；
- 本次服务、套餐或商品信息；
- “新增客户并继续”与“取消”按钮。

确认新增后再进入原操作确认，不得直接写入。

## 10. 客户账本 Sheet

### 10.1 打开与关闭

- 点击底部“客户”后，从页面底部打开；
- 移动端高度建议为视口的85%～92%；
- 顶部显示拖动条、标题和关闭按钮；
- 点击关闭返回对话，不丢失聊天状态；
- 第一版不要求手势拖动关闭，避免误触。

### 10.2 搜索

支持按以下内容搜索：

- 客户化名；
- 搜索别名；
- 后续正式版可扩展手机号。

搜索无结果时显示空状态和“新增客户”入口。

### 10.3 客户列表条目

每位客户只展示：

- 客户化名；
- 搜索别名；
- 最后一次消费的服务名称；
- 最后一次消费日期；
- 服务类型数量；
- 进入详情指示。

不在客户列表中展示某一张套餐的余额，因为客户可能同时拥有很多服务类型和套餐卡。

示例：

```text
小蓝 · 蓝蓝
最近：肩颈按摩 · 2026年8月20日
4类服务  ›
```

从未消费过的客户显示“暂无消费记录”。

“最后一次消费”只统计套餐核销和一次性服务；购买套餐和购买商品不改变这里展示的服务与日期。客户默认按最后消费日期从新到旧排列，从未消费的客户放在最后。

## 11. 客户概览

点击客户条目后进入客户概览，展示：

- 客户化名与别名；
- 最近消费日期；
- 服务类型总数；
- 有效套餐数量；
- 全部服务类型；
- 最近动态。

### 11.1 服务类型列表

按服务类型聚合，例如：

```text
肩颈按摩
最近消费：2026年8月20日
剩余1/3 · 查看详情 ›
```

每项展示：

- 服务名称；
- 最近消费日期；
- 套餐余额摘要或“一次性”；
- 进入服务详情指示。

当服务类型较多时：

- 服务列表在当前Sheet内滚动；
- 提供服务名称搜索；
- 有效套餐服务优先；
- 已停用或只有历史记录的服务放在后面；
- 不采用无限横向卡片排列。

### 11.2 最近动态

展示跨服务的最近记录，包括：

- 服务名称；
- 日期；
- 记录类型；
- 次数变化。

默认显示最近3～5条，提供“查看全部”。

## 12. 服务详情

从客户概览点击具体服务进入。

### 12.1 顶部信息

- 返回客户服务列表；
- 服务名称；
- 最近消费日期；
- 编辑入口。

### 12.2 套餐卡列表

同一服务可能存在多张套餐卡，每张分别展示：

- 套餐标识；
- 总次数；
- 累计已用；
- 剩余次数；
- 购买日期；
- 可选价格；
- 套餐状态；
- 使用进度。

存在多张有效卡时，不自动合并成一个余额，也不替店主决定核销哪张。

### 12.3 一次性服务

没有套餐时显示：

```text
一次性服务
不计算套餐余额
```

### 12.4 该服务历史

只展示当前客户、当前服务的历史记录：

- 核销日期；
- 核销次数；
- 使用的套餐卡；
- 一次性服务标记；
- 可选价格；
- 记录来源：手动或Agent确认。

## 13. 数据同步规则

确认写入成功后，前端必须更新或重新获取：

1. 聊天确认卡；
2. 客户列表的最后消费服务与日期；
3. 客户概览的最近消费日期；
4. 对应服务类型的最近消费日期和余额摘要；
5. 服务详情的套餐余额、进度和历史；
6. 客户最近动态。

权威结果全部采用后端响应，不能依赖前端乐观计算作为最终值。

## 14. 视觉设计系统

### 14.1 当前视觉方向

名称：**纯净留白**。

特征：

- 白色主背景；
- 蓝紫色小面积强调；
- 细边框；
- 轻阴影；
- 中等圆角；
- 清晰黑灰文字；
- 不使用装饰性渐变。

### 14.2 色彩

| 用途 | 色值 |
|---|---|
| 主色 | `#5D75DB` |
| 主色浅背景 | `#EEF1FB` |
| 页面背景 | `#FFFFFF` |
| 次级表面 | `#F8F9FB` |
| 主文字 | `#262626` |
| 次级文字 | `#70757D` |
| 弱文字 | `#92969D` |
| 分隔线 | `#E4E7ED` |
| 成功 | `#2C765B` |
| 成功浅背景 | `#E2F4EB` |
| 警告 | `#B8752A` |
| 危险 | `#C65353` |

主色用于：

- 发送；
- 确认入账；
- 当前导航；
- 关键余额；
- 可点击文本。

不得大面积铺满页面。

### 14.3 字体层级

建议使用系统中文字体：

```css
-apple-system, BlinkMacSystemFont, "SF Pro Display", "PingFang SC", "Microsoft YaHei", sans-serif
```

| 层级 | 建议字号 | 字重 |
|---|---:|---:|
| 页面标题 | 20～24px | 650～750 |
| 卡片标题 | 16～18px | 650～750 |
| 正文 | 14～16px | 400～500 |
| 辅助文字 | 12～13px | 400～500 |
| 标签 | 11～12px | 600～750 |

实际移动端产品字号不得沿用视觉原型中为缩放展示而使用的过小字号。

### 14.4 间距

采用4px基础网格：

- 小间距：4px、8px；
- 组件内部：12px、16px；
- 区块之间：20px、24px；
- 页面左右安全边距：16px。

### 14.5 圆角

- 小按钮：10～12px；
- 输入框：16～18px；
- 普通卡片：14～16px；
- 大Sheet：24～28px；
- 标签：全圆角。

### 14.6 阴影

只用于：

- 浮动输入框；
- 客户Sheet；
- 当前待确认卡。

普通列表项优先使用边框，不叠加强阴影。

## 16. 前端数据类型建议

```ts
type CustomerSummary = {
  id: string;
  displayName: string;
  aliases: string[];
  lastConsumedServiceName: string | null;
  lastConsumedAt: string | null;
  serviceTypeCount: number;
};

type CustomerOverview = {
  id: string;
  displayName: string;
  aliases: string[];
  lastConsumedAt: string | null;
  serviceTypeCount: number;
  activePackageCount: number;
  services: ServiceSummary[];
  recentEntries: LedgerEntry[];
};

type ServiceSummary = {
  serviceId: string;
  serviceName: string;
  lastConsumedAt: string | null;
  activePackageCount: number;
  totalRemainingCount: number | null;
  isOneTimeOnly: boolean;
};

type AgentProposal = {
  id: string;
  originalInput: string;
  promptVersion: string;
  status: "pending" | "confirmed" | "cancelled" | "expired";
  actions: ProposedAction[];
};
```

具体字段以最终后端Schema为准，前端不得自行发明权威余额字段。

## 17. API对应关系

| 前端动作 | 后端接口 |
|---|---|
| 查看或搜索客户列表 | `GET /api/customers?search=&sort=last_consumed_desc` |
| 查看客户概览 | `GET /api/customers/{id}/overview` |
| 查看客户服务类型 | `GET /api/customers/{id}/services` |
| 查看某项服务详情 | `GET /api/customers/{id}/services/{service_id}` |
| 查看客户账本 | `GET /api/customers/{id}/ledger` |
| 创建套餐 | `POST /api/customers/{id}/packages` |
| 解析自然语言 | `POST /api/agent/interpret` |
| 查看解析建议 | `GET /api/agent/proposals/{id}` |
| 确认写入 | `POST /api/agent/proposals/{id}/confirm` |
| 取消建议 | `POST /api/agent/proposals/{id}/cancel` |
| 查看回收站 | `GET /api/trash` |
| 查看提示词 | `GET /api/settings/prompt` |
| 保存提示词版本 | `POST /api/settings/prompt/versions` |

如客户概览或服务详情数据不足，应优先扩展后端响应Schema，不在前端拼凑不可靠数据。

## 18. 页面状态

每个页面或组件必须设计：

- 初始状态；
- 加载状态；
- 空状态；
- 成功状态；
- 校验错误；
- 网络错误；
- 模型解析错误；
- 权限或会话失效；
- 数据被其他操作更新后的冲突状态。

### 18.1 余额冲突

如果预览生成后，套餐余额已变化：

- 后端拒绝旧预览直接写入；
- 前端保留原输入；
- 展示新余额；
- 要求店主重新确认。

### 18.2 无对应套餐

显示：

- “未找到可用套餐”；
- “补充套餐”；
- “改为一次性服务”；
- “取消”。

### 18.3 多张同类卡

显示所有候选卡的：

- 购买日期；
- 总次数；
- 剩余次数；
- 可选价格。

由店主选择后再核销。

## 19. 可访问性与可用性

- 正文实际字号不低于14px；
- 可点击区域建议不小于44×44px；
- 不能只依赖颜色表达成功或错误；
- 输入、按钮和Sheet支持键盘焦点；
- Sheet打开后焦点限制在Sheet内；
- 关闭Sheet后焦点返回“客户”入口；
- 日期同时使用机器值和中文显示；
- 动画时长控制在200～350ms；
- 尊重系统“减少动态效果”设置。

## 22. 核心验收用例

1. 输入“小蓝今天肩颈按摩1次”；
2. 聊天内出现解析确认卡；
3. 卡片显示核销日期和确认后余额；
4. 修改日期或次数后重新预检查；
5. 确认后卡片显示实际写入结果；
6. 客户列表中小蓝的最后消费服务和日期更新；
7. 进入小蓝后看到多种服务类型；
8. 进入肩颈按摩详情后看到套餐余额和新增历史；
9. 多张同类卡时必须选择具体卡；
10. 一次性服务不显示套餐余额；
11. 新客户必须确认创建后才能继续；
12. 删除数据二次确认并可从回收站恢复；
13. 修改系统提示词后可预览、激活和回退；
14. API Key不出现在任何前端内容中；
15. 购买套餐或商品后，客户列表中的“最后消费”不被覆盖；
16. 一组多项操作中任一项校验失败时，整组不产生账本记录；
17. 删除一次套餐核销后余额回退，从回收站恢复后余额重新扣减且结果正确。

## 24. 已确认决策

以下决策已于2026年8月20日确认：

1. 客户列表默认按最后消费日期从新到旧排列，从未消费的客户放在最后；
2. 一句话包含多项操作时，采用“逐项可修改＋最后统一确认入账”的方式，剩余项目全部成功或全部不写入；
3. 移动端和电脑本地测试均使用客户底部Sheet交互。

本文件自此作为前端开发基线v1.0。后续改变上述决策或核心流程时，应先更新文档并获得确认。
